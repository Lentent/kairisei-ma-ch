# 礼包兑换码

Linux 服务器接入 `cdk.ccgduckcloud.org` 的配置与步骤见 [Cloudflare 接入](CDK-CLOUDFLARE.md)。

后台新增「礼包兑换码」。玩家直接使用 APK 已有的礼包码兑换窗口，服务端已接入它调用的 `POST /GiftCodeAd`。无需修改或重新打包 APK。

游戏内兑换使用当前登录会话确定角色，游客也可兑换，无需另输账号密码。每种奖励发送一封原生礼物，在游戏邮件／礼物箱领取。

备用网页入口为游戏服务地址后的 `/cdk`，例如 `http://服务器IPv4:26020/cdk`；后台提供完整链接。网页使用已绑定的账号、密码和兑换码提交，游客需先绑定账号。两种入口共用奖励和限领记录，不能重复领取。使用游戏主端口，不使用只在本机开放的 Admin 端口。

## 创建与管理

1. 选择通用码或一次性码。通用码每个角色限领一次；全服总次数填 `0` 表示不限。一次性码全服只能使用一次。
2. 设置邮件标题、正文和有效期；开始时间留空立即生效，结束时间留空长期有效。后台时间按浏览器本机时区填写和显示，服务端按 Unix 时间检查。
3. 从现有奖励目录选择物品，设置数量；卡牌可设置等级、名声和爱情。数量及属性沿用运营发奖的限制，未进入运行资源清单的卡牌不能发放。
4. 指定 6–64 位字母、数字或短横线兑换码，或者留空自动生成。兑换时忽略首尾空格、统一转成大写。每批可生成 1–100 个随机码；指定码只能单个创建。
5. 保存后可复制、下载本次生成的兑换码。列表支持分页、停用／启用及查询奖励配置和兑换记录。停用只阻止后续兑换，已经发出的奖励不回收。

已创建的奖励和次数配置不可修改，需改变奖励时创建新码。兑换码不能删除或重新使用同一编号。启用旧码不会重置已兑换记录。

## 一致性与存储

配置复用 SQLite 的 `cn_global_operation`，键前缀为 `cdk:`；兑换记录复用 `cn_admin_action_receipt`，同时写入操作审计。不需要升级数据库结构。配置、记录、邮件随原存档数据库一起备份。

兑换持有与游戏请求共用的账号锁；同一笔事务检查最新配置、有效期、全服剩余次数，并保存邮件、兑换记录及审计。任一步失败都回滚。并发兑换不会突破总次数，同账号重复提交不会重复发奖，领取或删除邮件、重启服务器均不会解除领取限制。提交期间配置变化会返回冲突，玩家可重新提交。

游戏内请求限制为每个角色每分钟最多 12 次；网页按来源 IP 每分钟最多 12 次，密码验证最多 4 个并行请求。游戏会话、兑换码和网页密码不进入此入口的请求采集日志；请求体摘要、长度、查询参数和请求头也移除。

公网提供兑换页时，建议通过 HTTPS 反向代理发布，避免账号密码以明文 HTTP 传输；可以代理 `/cdk`、`/cdk.js`、`/api/cdk/redeem`，Admin 端口继续保持本机访问。

## 验收步骤

| 场景 | 操作及预期 |
| --- | --- |
| 正常兑换 | 创建通用码，配置金币、水晶各一项；在游戏内礼包码窗口提交后提示成功，收到两封礼物，领取后余额增加对应数量 |
| 游客兑换 | 未绑定账号的已登录游客可直接在游戏内兑换 |
| 跨入口防重 | 同角色在游戏内兑换后，再使用网页兑换同码，不能重复领取；反向操作同样生效 |
| 账号限领 | 同账号再次提交提示已经兑换；另一账号可领取通用码 |
| 一次性码 | 两账号同时兑换，只有一个成功，另一个提示次数已用完 |
| 总次数 | 通用码总次数设为 2，三个不同账号兑换，最多两次成功 |
| 有效期与停用 | 无效、未开始、过期、停用的码不能兑换，不产生记录 |
| 重复点击 | 同时提交多次只发一组礼物；游戏内重复点领取只到账一次 |
| 持久化 | 领取或删除邮件后重启服务，同账号仍不能再次兑换 |
| 后台操作 | 批量生成并下载；停用／启用；核对 UID、时间和邮件编号。启用后旧账号仍不能再领 |
| 登录校验 | 无效游戏会话不能兑换，也不能误弹成功；网页错误密码不能兑换，提供的 UID 不被接受，提交结束后密码框清空 |

自动检查覆盖事务失败回滚、并发领取、全服限额、记录分页、重启后防重、批量创建冲突回滚、停用与兑换竞争、身份校验、限流、日志脱敏，以及游戏业务接口中的邮件领取和删除。实际 APK 可按上述步骤做一次玩家端验收。

## 接口

| 入口 | 方法及路径 | 作用 |
| --- | --- | --- |
| 游戏内 | `POST /GiftCodeAd` | 原生会话前缀及 JSON `{ "channel": "渠道", "codenumber": "兑换码" }`；角色由服务端验证会话确定 |
| 玩家 | `GET /cdk` | 兑换网页 |
| 玩家 | `POST /api/cdk/redeem` | JSON `{ "username": "账号", "password": "密码", "code": "兑换码" }`；请求头 `X-Kairisei-CDK: 1` 和 `Content-Type: application/json` |
| Admin | `GET /api/cdk?limit=20&offset=0` | 分页列出兑换码及使用次数 |
| Admin | `POST /api/cdk` | 创建；字段 `code`、`count`、`mode`（`shared` / `single`）、`title`、`message`、`start_unix`、`expires_unix`、`max_uses`、`rewards` |
| Admin | `PUT /api/cdk/{code}/enabled` | JSON `{ "enabled": false, "revision": 1 }`；版本冲突返回 409 |
| Admin | `GET /api/cdk/{code}/records?limit=20&offset=0` | 分页记录，同时返回奖励配置及目录名称 |

Admin 写接口沿用本机来源限制及 `X-Kairisei-Admin-Action: apply` 请求头。奖励数组使用原发奖格式，例如 `{ "reward_type": 4, "reward_type_id": 0, "quantity": 100 }`。网页接口验证账号密码；两种玩家入口均不接受自选 UID。

原生协议根据当前 APK 的 `GiftCodeWindow.sendCode`、`ProtoGen.GiftCodeAdReceive` 和配套字符串表确认。返回保持三行协议，业务行包含整数 `code`：`0` 成功、`1` 无效／未开始／停用、`2` 过期、`3` 已使用／次数耗尽、`5` 服务异常、`8` 无效会话／角色不存在、`9` 请求过于频繁。业务失败仍使用正常公共协议头，让原生窗口读取错误码；负公共错误码会让该客户端跳过业务解析并误判默认值为成功。当前兑换码不设置渠道限制，`channel` 不参与身份判断。
